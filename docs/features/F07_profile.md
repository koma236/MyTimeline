# 機能定義書 F07: プロフィール表示・編集

**関連:** 要件 [04_features.md](../04_features.md) 5.8 / ユースケース [03_usecases.md](../03_usecases.md) UC-12 / 画面 [06_ui_design.md](../06_ui_design.md) SCR-05・SCR-07 / データ [07_er_diagram.md](../07_er_diagram.md) `users`

## 1. 概要 / 目的
ユーザーの情報（表示名・自己紹介・プロフィール画像）を閲覧・編集できるようにする。投稿やコメントに表示されるユーザー名からプロフィールへ辿れるようにし、「誰が書いたのか」を確認する導線を用意する。

[08_constraints.md](../08_constraints.md) TBD-06 で初期スコープ外としていたプロフィール編集を、この機能で決定・実装した。

フォロー／フォロワー数とフォローボタンは [F06](F06_follow.md) の範囲であり、本機能には含まない。

## 2. 機能詳細
- **プロフィール表示:** 表示名・`@username`・自己紹介・プロフィール画像・利用開始年月・その人の投稿一覧（新しい順）
- **プロフィール編集（本人のみ）:** 表示名・自己紹介を変更する
- **プロフィール画像:** JPEG / PNG をアップロードして差し替える。削除すると既定の表示（表示名の頭文字）に戻る
  - 表示名・自己紹介のフォームとは分け、選択した時点で即時反映する。1 つの保存ボタンで JSON と画像を続けて送ると、片方だけ成功した状態をユーザーに説明できなくなるため
- **プロフィールへの導線:** 投稿・コメントに表示されるユーザー名とプロフィール画像はすべてプロフィール（SCR-05）へのリンク（06_ui_design.md 7.1 の共通ルール）
- **username とメールアドレスは変更できない。** 前者は他人からの参照先（URL）になり、後者はログイン手段なので、プロフィール編集とは別の手続きとする

## 3. 対象画面
- SCR-05 プロフィール画面（情報・プロフィール画像・投稿一覧・自分なら編集への導線）
- SCR-07 プロフィール編集画面（表示名・自己紹介・プロフィール画像）

## 4. API エンドポイント

| メソッド | パス | 説明 | 認証 |
|----------|------|------|------|
| GET | `/api/users/{username}` | プロフィール取得 | 要 |
| GET | `/api/users/{username}/posts?cursor=&limit=` | 対象ユーザーの投稿一覧 | 要 |
| PUT | `/api/users/me` | 表示名・自己紹介の更新 | 要 |
| PUT | `/api/users/me/avatar` | プロフィール画像のアップロード（`multipart/form-data`・パート名 `file`） | 要 |
| DELETE | `/api/users/me/avatar` | プロフィール画像の削除 | 要 |

**参照は `{username}`、編集は `/me`。** プロフィールの URL は人が読めた方がよく、画面上のリンクとも一致する。一方で編集できるのは本人だけなので、ID を受け取る意味がない。受け取れば必ず所有者チェックが要るが、パスを `/me` に固定すれば他人を書き換える経路自体が存在しなくなる（このため F03・F04 と違い 403 が発生しない）。

**返す DTO を用途で分ける。** `GET /api/users/{username}` は `ProfileResponse` を返し、**メールアドレスを含めない**。誰でも開ける画面なので、メールアドレスを持つ `UserResponse` をそのまま返すと個人情報が漏れる。編集系（`/me`）は本人しか叩けないので `UserResponse` を返し、クライアントはそれをログイン中ユーザーの状態にそのまま反映できる。

**プロフィール画像削除は 204 ではなく更新後の `UserResponse` を返す。** クライアントが再取得せずに画面を揃えられる（F05 の `LikeResponse` と同じ考え方）。

**プロフィール画像削除を独立したエンドポイントにする。** 「空のファイルを送る＝削除」にすると、通信事故で中身が空になったのか意図的な削除なのかを区別できない。

## 5. データ
- `users.display_name`（VARCHAR(100) NOT NULL）
- `users.bio`（VARCHAR(300)・NULL 可）— V1 で作成済みだったが、本機能で初めて読み書きされる
- `users.avatar_key`（VARCHAR(512)・NULL 可）— V6 で追加。**画像本体は保存せず、オブジェクトストレージのキーだけを持つ**
- 画像本体はローカルでは MinIO、本番では AWS S3 に置く（[09_infrastructure.md](../09_infrastructure.md)）
- キーの規約: `avatars/{userId}/{UUID}.{拡張子}`
  - ファイル名にユーザーの入力を一切使わない。アップロード時のファイル名を流用すると `../` を含む名前でキー空間を汚されうる
  - 拡張子は申告値ではなく、検出した実フォーマットから決める
  - 更新のたびにキーが変わるので、古い画像がブラウザや CDN のキャッシュに残らない
- 投稿一覧は F02 と同じカーソルページング（id の降順・既定 20 件・上限 50 件）。`idx_posts_user_id (user_id, id DESC)` が絞り込みと並び替えの両方を賄う

### プロフィール画像 URL の受け渡し
DB はキーしか持たないため、API は**期限付きの署名付き URL**（既定 60 分）を `avatarUrl` として返す。バケットを公開せずに済み、URL が漏れても期限が切れれば無効になる。

トレードオフとして、発行のたびに URL が変わるためブラウザキャッシュが効かない。本番で CloudFront に載せる際は署名付き Cookie や OAC で URL を安定させる方が望ましい（08_constraints.md に TBD として記載）。

## 6. バリデーション / 制約
- 表示名：必須・100 文字以内（`SignupRequest` と同じ制約・同じ文言にする。片方だけ変えると「登録できたのに編集で弾かれる」ちぐはぐな挙動になる）
- 自己紹介：任意・300 文字以内（`users.bio VARCHAR(300)` に合わせる）
  - 空文字・空白のみは `NULL` に正規化して保存する。DB のコメントが「未設定は NULL」と宣言している以上、`''` と `NULL` の 2 通りの未設定を混在させない
- プロフィール画像：
  - 形式は JPEG / PNG のみ
  - サイズは 2MB 以内、縦横は 4096 ピクセル以内
  - **申告された Content-Type とファイル名の拡張子は信用せず、バイト列の中身から実フォーマットを判定する。** どちらも簡単に詐称でき、実体が画像でないファイルを保存すると画像の URL から任意のコンテンツを配れてしまう
  - 判定はヘッダのみを読む（`ImageIO.read()` で全画素をデコードすると、小さなファイルで巨大な寸法を宣言する画像でメモリを食い潰される）
- multipart の上限（6MB）はアプリ側の上限（2MB）より大きく設定する。同じにすると Spring が先に弾いてしまい、項目付きの丁寧なエラーを返せない

### プロフィール画像更新の順序
1. 検証（不正ならストレージに触れずに 400）
2. 新しい画像を保存
3. DB のキーを更新
4. 古い画像を削除（失敗しても警告のみ）

逆順にすると途中で失敗したときに「DB はキーを指しているのに実体が無い」という壊れ方をする。この順序なら最悪でも参照されないオブジェクトが 1 個残るだけで、画面の見え方は変わらない。ストレージへの操作はトランザクションでロールバックできないため、孤児の発生は許容する。

## 7. エラーハンドリング / 異常系
- 存在しない username：**404**（`ProfileNotFoundException`）
  - 投稿一覧も空配列ではなく 404 を返す。空配列だと「そんなユーザーはいない」と「まだ投稿していない」を画面が区別できない
  - 認証側の `UserNotFoundException`（トークンは有効なのに本人のレコードが無い＝401）とは別物なので流用しない
- 不正な画像：**400**。理由（空・サイズ超過・非対応形式・寸法超過）を `fieldErrors.avatar` に入れ、他の入力エラーと同じ形にする。クライアントはファイル選択欄の直下にそのまま表示できる
- multipart の上限超過：**400**（HTTP としては 413 が正確だが、本アプリは「リクエストの作り方の誤り」を一貫して 400 で返している）
- `file` パートが無い：**400**（拾わないと catch-all の 500 になる）
- プロフィール画像が未設定のまま削除：エラーにせず現状維持（冪等）

# 機能定義書 F05: いいね

**関連:** 要件 [04_features.md](../04_features.md) 5.6 / ユースケース [03_usecases.md](../03_usecases.md) UC-09 / 画面 [06_ui_design.md](../06_ui_design.md) SCR-03・SCR-04 / データ [07_er_diagram.md](../07_er_diagram.md) `likes`

## 1. 概要 / 目的
投稿への「いいね」を付与・取り消しできるようにし、投稿ごとのいいね数を可視化する。第三者のいいねを想定する。

## 2. 機能詳細
- 投稿のいいねボタンでいいね／取り消しをトグルする
- 1 ユーザーにつき 1 投稿 1 回まで（`likes(post_id, user_id)` の UNIQUE 制約で二重いいねを防止）
- いいね状態はボタンの色で表現（自分がいいね済みかどうか）
- いいね数はタイムライン・投稿詳細の両方に表示

## 3. 対象画面
- SCR-03 タイムライン画面（各投稿カードのいいねボタン）
- SCR-04 投稿詳細画面

## 4. API エンドポイント案

| メソッド | パス | 説明 | 認証 |
|----------|------|------|------|
| POST | `/api/posts/{postId}/like` | いいねを付与 | 要 |
| DELETE | `/api/posts/{postId}/like` | いいねを取り消し | 要 |

どちらも操作後の状態 `{ likeCount, likedByMe }` を返す。クライアントはこれだけでボタンの見た目を更新でき、投稿を取り直さずに済む。

「押すたびに反転」する 1 本のトグルにはしない。トグルだと通信が再送されたときに意図と逆の状態になりうるが、付与と取り消しを分ければどちらを何度呼んでも結果は同じになる。

なお、いいね数と自分のいいね状態はタイムライン・投稿詳細のレスポンス（`PostResponse` の `likeCount` / `likedByMe`）にも含まれる。これらの API は表示のために別途叩く必要はない。

## 5. データ
- `likes`（id, post_id, user_id, created_at）、複合 UNIQUE `(post_id, user_id)`
- いいね数：`likes` を `post_id` で `COUNT`（非正規化カウンタは持たない。07_er_diagram.md 8.4）
- 自分のいいね状態：ログインユーザーの `likes` 有無
- UNIQUE `(post_id, user_id)` のインデックスが、いいね数の `COUNT`（`post_id` で絞る）と自分のいいね状態の `EXISTS`（`post_id` + `user_id`）の両方を賄う
- どちらもタイムラインの投稿ごとに必要になるが、投稿を取得する SQL の中で一緒に集計する（N+1 を作らない）

## 6. バリデーション / 制約
- 同一ユーザーの二重いいねは UNIQUE 制約で拒否（冪等に扱う）
  - アプリ側の事前 SELECT ではなく `INSERT ... ON CONFLICT DO NOTHING` で DB に任せる。同時に 2 回押されたときに両方が「まだ無い」と判定して 2 行入るのを防ぐため
- 対象投稿が存在すること
- 自分の投稿へのいいねは許可（仕様として制限しない）。X も同じ挙動

## 7. エラーハンドリング / 異常系
- 既にいいね済みで再度 POST：エラーにせず現状維持（冪等）として扱う
- 未いいねで DELETE：同様に冪等として扱う
- 存在しない投稿：404

# 機能定義書 F06: フォロー・ユーザー検索

**関連:** 要件 [04_features.md](../04_features.md) 5.7 / ユースケース [03_usecases.md](../03_usecases.md) UC-10〜12 / 画面 [06_ui_design.md](../06_ui_design.md) SCR-05・SCR-06 / データ [07_er_diagram.md](../07_er_diagram.md) `follows`・`users`

## 1. 概要 / 目的
ユーザー同士のフォロー関係を管理し、フォロー中タイムライン（F02）の対象を決定する。フォローする相手を見つけるために、ユーザー検索と、投稿・コメントからのプロフィール遷移の 2 つの導線を提供する。

## 2. 機能詳細
- **フォロー / 解除:** プロフィール（SCR-05）または検索結果（SCR-06）のフォローボタンでトグルする
  - 自分自身はフォロー不可
  - 二重フォローは `follows(follower_id, followee_id)` の UNIQUE 制約で防止
- **フォロー/フォロワー数表示:** プロフィールに表示（`follows` の集計）
- **ユーザー検索:** 検索バーで username / 表示名を**部分一致**検索し、結果一覧を表示。未入力時は発見用に全ユーザー/新着ユーザーを表示
- **プロフィール遷移導線:** 投稿・コメント・検索結果に表示されるユーザー名はすべてプロフィール（SCR-05）へのリンクとし、そこからフォローできる
- **フォロー中タイムラインの対象:** 「自分＋自分がフォローしているユーザー」（F02）

## 3. 対象画面
- SCR-05 プロフィール画面（情報・フォロー/フォロワー数・フォローボタン・投稿一覧）
- SCR-06 ユーザー検索画面（検索バー・結果一覧）

## 4. API エンドポイント

| メソッド | パス | 説明 | 認証 |
|----------|------|------|------|
| GET | `/api/users/search?q=&cursor=&limit=` | username/表示名の部分一致検索 | 要 |
| GET | `/api/users/{username}` | プロフィール取得（`followingCount`, `followerCount`, `followingByMe`） | 要 |
| GET | `/api/users/{username}/posts` | 対象ユーザーの投稿一覧（F07 で実装済み） | 要 |
| POST | `/api/users/{userId}/follow` | フォロー | 要 |
| DELETE | `/api/users/{userId}/follow` | フォロー解除 | 要 |

**フォローの登録と解除を分ける。** 「押すたびに反転」する 1 本のトグルにすると、通信が再送されたときに意図と逆の状態になりうる。POST / DELETE に分ければ何度呼んでも結果は同じ（冪等）で、いいね（F05）と同じ形になる。

**参照は `{username}`、フォローは `{userId}`。** プロフィールの URL は人が読めた方がよく画面上のリンクとも一致するが、フォローは「画面に出ているユーザー」への操作でクライアントは必ずその id を持っている。id に寄せておけば、将来 username を変更できるようにしても経路が壊れない。

**フォロー / 解除は操作後の状態（`FollowResponse`）を返す。** 返すのは対象ユーザーのフォロワー数とフォロー状態の 2 つだけ。クライアントはこれでボタンと数字を更新でき、プロフィールを取り直さずに済む（F05 の `LikeResponse` と同じ考え方）。手元で ±1 する方式にしないのは、他の人のフォローで数がずれていたときにそのずれが残り続けるため。

**検索結果は `UserSummary`（`ProfileResponse` とは別の DTO）。** 検索結果カードにフォロー中数・フォロワー数は出さないので、一覧の件数分だけ集計を走らせる理由がない。

**`/api/users/search` は `/api/users/{username}` より優先される。** Spring は変数を含むパターンより固定の文字列を優先するため、定義順に関係なく検索として扱われる。その代わり `search` という username のプロフィールは開けない（現時点では許容し、必要になれば予約語として登録時に弾く）。

## 5. データ
- `follows`（id, follower_id, followee_id, created_at）— V7 で作成
  - 複合 UNIQUE `(follower_id, followee_id)`、チェック制約 `follower_id <> followee_id`
  - UNIQUE インデックスが `(follower_id, ...)` の順なので、フォロー中数の COUNT・フォロー先の一覧・フォロー済みかの EXISTS はすべてこれ 1 本で賄える
  - フォロワー数（`followee_id` で絞る）とユーザー削除時の CASCADE のために `idx_follows_followee_id` を別に張る
- フォロー中数：`follows` を `follower_id` で `COUNT`
- フォロワー数：`follows` を `followee_id` で `COUNT`
- 検索対象：`users.username` / `users.display_name`

**非正規化カウンタを持たない**（[07_er_diagram.md](../07_er_diagram.md) 8.4）。いずれの集計もインデックスだけで完結し、カウンタを持つとフォロー操作のたびに 2 テーブルを整合させる責任が増える。

### フォロー中タイムラインの組み立て
`follows` からフォロー先の id を引き、自分の id を足して投稿の絞り込み条件（`IN`）に渡す。タイムラインの SQL に `follows` を JOIN する手もあるが、そうすると「自分の投稿も含める」という条件まで SQL 側に混ざる。フォロー数が数千規模になるまでは、この形の方が読み解きやすい。

### 検索の実装
- `ILIKE '%...%'` で**大文字小文字を区別しない部分一致**。username は小文字だけだが表示名は任意の文字列で、「Taro」と入力して「taro さん」が出ないのは検索として不便
- **検索語のワイルドカード（`%` `_`）とエスケープ文字はサーバー側でエスケープする。** 素通しにすると `%` 一文字の検索が全ユーザーに一致し、「入力した文字を含むユーザー」という検索の意味が壊れる
- 並びは `id` の降順、ページングはタイムラインと同じカーソル方式。この並びのまま「未入力時は新着ユーザー」も満たせる
- パスワードハッシュとメールアドレスは **SELECT の対象にしない**。他人の情報を並べる画面なので、そもそも読まないのが確実
- 結果のフォロー状態は、自分のフォロー先を 1 回引いて突き合わせて決める（件数分の EXISTS を流すと N+1 になる）
- 自分自身も結果に含める。除外すると「自分の名前で検索したのに出てこない」という分かりにくい挙動になるため、画面側でフォローボタンを出さない扱いにしている

## 6. バリデーション / 制約
- 自分自身のフォロー：**400**（`SelfFollowException`）。UI ではボタンを表示しない
  - F06 の当初案は「422/400」だったが、本アプリは受け付けられないリクエストを一貫して 400 で返しているため 400 に寄せる
  - DB のチェック制約でも弾けるが、それだけだと 500 になってしまうのでアプリ側で先に判定する
- 二重フォロー：UNIQUE 制約で防止（`ON CONFLICT DO NOTHING` で冪等に扱う）
  - 「無ければ INSERT」をアプリ側の SELECT で判定すると、連打で 2 回同時に来たときにどちらも「無い」と判定して 2 行入りうる
- 検索キーワード：50 文字以内（超過は 400）
- 検索の `limit`：既定 20 件・上限 50 件（タイムラインと同じ。超過は黙って上限に丸める）

## 7. エラーハンドリング / 異常系
- 自分自身をフォロー要求：**400**
- 既フォローで再 POST / 未フォローで DELETE：**200**（冪等。現在の状態を返す）
- 存在しないユーザー：**404**（`ProfileNotFoundException`）
- 検索結果 0 件：「該当するユーザーがいません」を表示
- 「フォロー中」タブが 0 件：ユーザー検索（SCR-06）への導線を表示する（UC-04 代替フロー）

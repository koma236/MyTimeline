# 14. 障害対応運用フロー

> **前提:** 本ドキュメントは、[11_monitoring_design.md](11_monitoring_design.md) のアラートが鳴った（または利用者から報告があった）ときに **誰が・何を・どの順で** 行うかを定める。
> 学習用プロジェクトのため専任のオンコール体制は無く、「担当者 = リポジトリのメンテナ」を前提にしている。体制ができたら [14.1](#141-重大度と初動目標) の連絡先を差し替える。

### 14.1 重大度と初動目標

| 重大度 | 定義 | 例 | 確認開始 | 暫定対処の目標 | 周知 |
|--------|------|----|----------|----------------|------|
| **SEV1** | 全利用者が主要機能（ログイン / タイムライン / 投稿）を使えない | readiness DOWN（M-01）、5xx 率 5 % 超（M-03 Critical）、DB 接続取得失敗（M-12） | 15 分以内 | 1 時間以内 | 第一報を即時、以後 30 分ごと |
| **SEV2** | 一部機能または一部利用者に影響。回避策がある | 画像投稿だけ失敗（M-17）、p99 が 5 秒超（M-06 Critical）、JVM ヒープ 90 %（M-08 Critical） | 1 時間以内 | 当日中 | 第一報と復旧報 |
| **SEV3** | 利用者影響なし、または軽微。兆候段階 | Warning 全般、ERROR ログ 1 件、401 の急増（M-14 Warning） | 翌営業日 | 1 週間以内に原因記録 | 不要（チケットで管理） |

迷ったら **1 段階重く** 判定し、状況が分かった時点で下げる。

### 14.2 対応フロー

```
 検知（アラート / 利用者報告）
   │
   ▼
 ① 受理・重大度判定（〜15 分）          担当者がアラートを「確認中」にし、SEV を仮決めして障害チャンネルに第一報
   │
   ▼
 ② 一次切り分け（〜30 分）              14.3 の手順で「どこが壊れているか」を特定。直近デプロイの有無を最初に確認
   │
   ├── 原因が直近デプロイ ──▶ ③-a ロールバック（14.5）
   ├── 原因が依存先（DB / S3）──▶ ③-b 依存先の復旧 or 回避（Runbook RB-06 / RB-08）
   └── 原因不明 ──▶ ③-c 再起動で回避を試み、ログ・ヒープダンプを保全してから調査
   │
   ▼
 ④ 復旧確認                              readiness UP、5xx 率・p95 が平常値、主要操作（ログイン→投稿→タイムライン）を手で確認
   │
   ▼
 ⑤ 復旧報・クローズ                      障害チャンネルに復旧報。アラートを解決済みに
   │
   ▼
 ⑥ 恒久対策・ポストモーテム（SEV1/2 は必須、5 営業日以内）  14.7 のテンプレートで記録し、対策を Issue 化
```

### 14.3 一次切り分け手順

上から順に。**1 つ目で当たりが付いたら先に進まず対処に移る。**

| # | 確認 | コマンド / 見る場所 | 分かること |
|---|------|---------------------|------------|
| 1 | 直近 24 時間にデプロイしたか | `curl -s -H "Authorization: Bearer <token>" http://<host>:8080/actuator/info`、デプロイ履歴 | デプロイ起因ならロールバックが最短 |
| 2 | プロセスは生きているか | `curl -s http://<host>:8080/actuator/health/liveness` | 応答なし → プロセス / ホスト障害（RB-01） |
| 3 | DB に繋がっているか | `curl -s http://<host>:8080/actuator/health/readiness` | `DOWN` → DB 障害 or 接続設定（RB-06） |
| 4 | 何が ERROR を出しているか | `docker compose logs --since 30m backend \| grep '^{' \| jq -c 'select(.level=="ERROR") \| {ts:."@timestamp", logger:.logger_name, message, path:."http.url_details.path"}'` | 出力元クラスで原因の層（Storage / Mapper / Handler）が分かる |
| 5 | 特定リクエストの全行 | `... \| jq -c 'select(.request_id=="<X-Request-Id>")'` | 利用者報告から 1 リクエストを再現 |
| 6 | 特定の利用者だけか | `... \| jq -c 'select(."usr.id"=="<id>")'` | 1 人だけなら データ起因の可能性 |
| 7 | 遅いだけか | `/actuator/metrics/http.server.requests?tag=uri:/api/timeline/following` の `MAX` / `TOTAL_TIME` | 特定 API のみ遅い → SQL / S3 署名（RB-03） |
| 8 | 資源が枯渇していないか | `/actuator/metrics/jvm.memory.used`, `hikaricp.connections.pending`, `tomcat.threads.busy` | 飽和 → RB-05 / RB-06 |
| 9 | 外部（S3）か | ログの `logger_name` が `S3StorageService`、MinIO / S3 コンソールの状態 | RB-08 |

テキスト形式（ローカル）の場合は `jq` の代わりに `grep 'rid=<id>'` / `grep ' ERROR '` で同じことができる。

### 14.4 Runbook（アラート別）

#### RB-01 readiness / liveness が応答しない（M-01, M-02）

| 項目 | 内容 |
|------|------|
| 症状 | `/actuator/health/*` がタイムアウト or 503。利用者は全操作不可（SEV1） |
| 確認 | ホストに入れるか → `docker compose ps` / `systemctl status mytimeline` → プロセス有無。`readiness` だけ DOWN なら DB（RB-06 へ） |
| 想定原因 | OOM でプロセス死亡、デプロイ失敗で起動していない、ポート競合、ホスト障害 |
| 暫定対処 | 起動ログ（`docker compose logs backend \| head -200`）で起動失敗理由を確認 → 設定誤りなら修正して再起動。OOM なら `-Xmx` 見直しのうえ再起動し、ヒープダンプ採取（RB-05） |
| エスカレーション | 再起動しても 10 分以内に UP にならない → ロールバック（14.5） |

#### RB-02 5xx 率・ERROR ログの増加（M-03, M-04, M-19）

| 項目 | 内容 |
|------|------|
| 症状 | 一部 / 全部のリクエストが 500。画面に「サーバーでエラーが発生しました」 |
| 確認 | 14.3 #4 で ERROR の `logger_name` と `stack_trace` を見る。`http.url_details.path` で特定 API に偏っているか。`version` が直近デプロイのものか |
| 想定原因 | デプロイした不具合、DB スキーマ不整合（Flyway 失敗）、依存先障害、想定外の入力 |
| 暫定対処 | 直近デプロイ起因 → ロールバック。特定 API のみ → その機能をフロントで一時的に隠す判断。依存先 → RB-06 / RB-08 |
| エスカレーション | 5xx 率 5 % 超が 15 分続く → SEV1 としてロールバック優先 |

#### RB-03 レイテンシ悪化・スレッド枯渇（M-05, M-06, M-13）

| 項目 | 内容 |
|------|------|
| 症状 | 画面が遅い。タイムアウト。5xx は出ていない |
| 確認 | `/actuator/metrics/http.server.requests` を `uri` 別に見て遅い API を特定。`hikaricp.connections.pending`（DB 待ち）、`tomcat.threads.busy`（スレッド詰まり）、`jvm.gc.pause`（GC） |
| 想定原因 | 遅い SQL（`ILIKE` 検索 TBD-12、`IN` 肥大 TBD-13）、S3 署名 URL 生成の遅延、GC、トラフィック急増 |
| 暫定対処 | DB 側で長時間クエリを確認（`pg_stat_activity`）→ 必要なら kill。GC なら再起動で一旦回復させヒープ調査。トラフィック急増なら M-14/15 で攻撃でないか確認 |
| エスカレーション | p99 5 秒超が 30 分継続、または readiness が落ち始めたら SEV1 |

#### RB-04 リクエスト数の急減（M-07）

| 項目 | 内容 |
|------|------|
| 症状 | アプリは正常なのに利用者が来ない |
| 確認 | ブラウザでフロント URL を開く。CloudFront / S3 静的ホスティング / DNS の状態。ALB のターゲットが healthy か |
| 想定原因 | フロント配信障害、DNS / 証明書期限切れ、ALB 設定変更、CORS 設定変更（`CORS_ALLOWED_ORIGINS`）で全リクエストがブラウザ側で失敗 |
| 暫定対処 | フロントの直近デプロイを戻す。CORS は `.env` を前の値へ |
| エスカレーション | インフラ層の障害 → [09_infrastructure.md](09_infrastructure.md) の構築担当へ |

#### RB-05 JVM ヒープ高止まり・GC 停止（M-08, M-09）

| 項目 | 内容 |
|------|------|
| 症状 | 徐々に遅くなり、最終的に OOM で落ちる |
| 確認 | `/actuator/metrics/jvm.memory.used?tag=area:heap` が GC 後も下がらないか。`jvm.gc.pause` の頻度 |
| 想定原因 | メモリリーク、巨大なレスポンス（ページングなしの一覧）、画像バイト列の保持、`-Xmx` 未設定でコンテナ上限と不整合 |
| 暫定対処 | 再起動前に `jcmd <pid> GC.heap_dump /tmp/heap.hprof` でダンプ採取 → 再起動。`JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75` 等でコンテナメモリに合わせる |
| エスカレーション | 再起動後 24 時間以内に再発 → リーク調査を Issue 化して優先対応 |

#### RB-06 DB コネクション枯渇・接続失敗（M-10, M-11, M-12, readiness DOWN）

| 項目 | 内容 |
|------|------|
| 症状 | readiness DOWN、`Connection is not available, request timed out after 30000ms`、タイムライン取得が 30 秒固まる |
| 確認 | `docker compose ps db` / RDS の状態。`hikaricp.connections.*`。DB 側 `SELECT count(*) FROM pg_stat_activity` と長時間トランザクション |
| 想定原因 | DB 停止 / フェイルオーバー、接続情報（`DB_*`）の誤り、ロック待ちでコネクションが返らない、プール上限（既定 10）不足 |
| 暫定対処 | DB 復旧待ち（アプリは readiness DOWN で自動的に振り分けから外れる。**liveness は UP のままなので再起動しない**）。ロック待ちは該当セッションを `pg_terminate_backend`。設定誤りは `.env` 修正 → 再起動 |
| エスカレーション | DB 自体の障害は RDS / DB 担当へ。アプリ側でできることは無い |

#### RB-07 認証失敗・認可拒否の急増（M-14, M-15, M-16, M-18）

| 項目 | 内容 |
|------|------|
| 症状 | 401 / 403 が平常の数十倍。利用者影響は通常なし（SEV3）。ログイン成功率が落ちていれば SEV2 |
| 確認 | ログを `network.client.ip` で集計（14.3 #4 の jq に `group_by`）。1〜数 IP に集中 → 攻撃。分散 → パスワード照合や DB の異常を疑い RB-02 へ |
| 想定原因 | ブルートフォース、クレデンシャルスタッフィング、ID 総当たり（403）、フロントのバグで古いトークンを送り続けている |
| 暫定対処 | 攻撃元 IP を ALB / セキュリティグループ / WAF で遮断（インフラ側）。アプリ側にはレート制限が無い（[08_constraints.md](08_constraints.md) TBD-17） |
| エスカレーション | 正規利用者のアカウントが乗っ取られた疑い → 該当ユーザーのリフレッシュトークンを DB で失効（`DELETE FROM refresh_tokens WHERE user_id = ?`）し本人に連絡 |

#### RB-08 S3 操作の失敗（M-17）

| 項目 | 内容 |
|------|------|
| 症状 | 画像付き投稿・アバター更新だけ失敗。テキスト投稿は成功（SEV2） |
| 確認 | ERROR ログの `stack_trace` で `AccessDenied` / `NoSuchBucket` / `UnknownHost` を見分ける。`S3_ENDPOINT` / `S3_BUCKET` / IAM ロールの設定 |
| 想定原因 | IAM ポリシー変更、バケット名の誤り、MinIO 停止（ローカル）、認証情報の期限切れ、S3 障害 |
| 暫定対処 | 設定誤り → `.env` / IAM 修正。S3 障害 → 復旧待ち（投稿画面で画像添付を一時的に案内） |
| エスカレーション | 失敗中に作成された投稿の孤児オブジェクト・欠損画像を復旧後に確認（TBD-11） |

### 14.5 ロールバック手順

1. 戻す先のバージョン（直前のリリースタグ / コミット）を決める。`/actuator/info` で現行の `version` を控える
2. **DB マイグレーションの互換性を確認する。** 戻す先のアプリが、現在のスキーマ（新しい Flyway バージョン）で動くか。テーブル・カラムの **削除** を含むマイグレーションを入れた直後は単純に戻せない → 前方修正（hotfix）を選ぶ
3. [09_infrastructure.md](09_infrastructure.md) 11.5 のデプロイ順序ルールに従い、**バックエンドを先に戻し、フロントを後に戻す**（フロントが新 API を期待したまま古いバックエンドに繋がる時間を最小にする）
4. 戻したあと readiness UP・主要操作の手動確認・M-03 / M-05 が平常値に戻ることを 15 分観察
5. 障害チャンネルへ「ロールバック完了（version X → Y）」を報告し、不具合修正の Issue を作成

### 14.6 連絡テンプレート

**第一報**

```
【障害 第一報】SEV{1|2} MYTIMELINE
発生時刻: 2026-MM-DD HH:MM（検知: アラート M-xx / 利用者報告）
影響: {全利用者 | 一部利用者} が {ログイン | 投稿 | 画像投稿 | タイムライン} を {できない | 遅い}
状況: 一次切り分け中。直近デプロイ {あり（version x.y.z, HH:MM） | なし}
次回報告: HH:MM
担当: @xxx
```

**経過報**

```
【障害 経過報】SEV{1|2} MYTIMELINE
原因（暫定）: {DB 接続枯渇 | デプロイ起因の NPE | S3 AccessDenied | 調査中}
対処: {ロールバック実施中 | 再起動済み・観察中 | DB 復旧待ち}
次回報告: HH:MM
```

**復旧報**

```
【障害 復旧報】SEV{1|2} MYTIMELINE
復旧時刻: HH:MM（影響時間: N 分）
原因: ...
対処: ...
恒久対策: ポストモーテムを MM/DD までに作成。Issue #N
```

### 14.7 ポストモーテム テンプレート

SEV1 / SEV2 は必須。`docs/postmortems/YYYY-MM-DD-<slug>.md` に残す（ディレクトリは初回作成時に追加）。**個人を責めない**（何が起きたかと、仕組みでどう防ぐかだけを書く）。

```markdown
# ポストモーテム: <タイトル>

| 項目 | 内容 |
|------|------|
| 発生日時 / 復旧日時 | 2026-MM-DD HH:MM 〜 HH:MM（影響 N 分） |
| 重大度 | SEV1 / SEV2 |
| 影響 | 誰が・何を・どれくらい（例: 全利用者が 25 分間ログイン不可。失敗リクエスト約 N 件） |
| 検知 | アラート M-xx / 利用者報告（検知までの時間） |
| 担当 | @xxx |

## タイムライン（JST）
- HH:MM 事象発生（後から判明）
- HH:MM アラート M-xx 発報
- HH:MM 担当者が確認開始（第一報）
- HH:MM 原因特定（request_id: ...）
- HH:MM ロールバック完了
- HH:MM 復旧確認・復旧報

## 根本原因
（技術的に何が起きたか。ログの抜粋・request_id を添える）

## うまくいったこと / いかなかったこと
- 検知は早かったか。閾値は適切だったか
- 切り分けに必要なログ・メトリクスは揃っていたか（足りなかったものを列挙）
- 手順（Runbook）は役に立ったか

## 恒久対策（アクションアイテム）
| # | 対策 | 種別（再発防止 / 検知改善 / 影響軽減） | 担当 | 期限 | Issue |
|---|------|------|------|------|-------|
| 1 | ... | ... | @xxx | MM/DD | #N |
```

### 14.8 訓練と見直し

- 本番開始前に **机上訓練** を 1 回行う: RB-06（DB 停止）と RB-02（デプロイ起因の 500）を `docker compose stop db` / 意図的なバグで再現し、本フローで復旧まで通す
- 四半期に 1 回、Runbook のコマンドが現行の構成で動くことを確認する（エンドポイント名・環境変数名の変更に追従）
- ポストモーテムの「足りなかったログ・メトリクス」は [10_logging_design.md](10_logging_design.md) / [11_monitoring_design.md](11_monitoring_design.md) に反映する

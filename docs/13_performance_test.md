# 15. パフォーマンステスト

> **前提:** 対象は **バックエンド API**、実行場所は **ローカルの Docker Compose** のみ。本番相当環境（EC2 / RDS / ALB）は未構築（[09_infrastructure.md](09_infrastructure.md)）のため、ここで得る数値は**絶対値ではなく、同じマシンでの前回との比較**に使う。
> 実行手順は [perf/README.md](../perf/README.md) を参照。

### 15.1 位置づけ

- **任意のタイミングで手動実行する。** CI（`.github/workflows/`）でも quality-check スキルでも実行しない
  - 1 回に数分〜1 時間かかり、PR ごとに回すには重い
  - 共有ランナーは性能が安定せず、合否を自動判定しても信用できない
- 実行の目安: 性能に効きそうな変更（SQL・インデックス・ページング・画像 URL 生成・コネクションプール設定）の前後、および [08_constraints.md](08_constraints.md) の性能に関する未決事項（TBD-09 / 12 / 13）に手を入れるとき

### 15.2 ツール

[k6](https://k6.io/)（`grafana/k6` の Docker イメージ、1.x 系で固定）。

| 理由 | 内容 |
|---|---|
| インストール不要 | Docker イメージで動く。compose の `profiles: ["perf"]` で通常起動からは外してある |
| 合否を自動判定できる | `thresholds` に違反すると非ゼロで終了する |
| レビューしやすい | シナリオが JavaScript のテキストなので、PR で差分を読める |

### 15.3 合否基準

[05_nonfunctional.md](05_nonfunctional.md) と [11_monitoring_design.md](11_monitoring_design.md) の数値をそのまま使う。性能テスト専用の基準は作らない。

| 指標 | 基準 | 出典 |
|---|---|---|
| 読み取り（`type:read`）の p95 | 1 秒未満 | 非機能要件「通常操作は 1 秒以内」、監視閾値「p95 1 秒」 |
| 書き込み（`type:write`）の p95 | 1 秒未満 | 同上 |
| リクエスト失敗率 | 1 % 未満（stress は 5 % 超で自動中断） | 監視閾値「5xx 率 1 % / 5 %」 |

認証（`type:auth`）は BCrypt が意図的に重いため、上の基準とは別枠で集計する。

### 15.4 テスト環境

`perf/docker-compose.perf.yml` を `docker-compose.yml` に重ねて使う。

| 項目 | 設定 | 理由 |
|---|---|---|
| データベース | 同じ Postgres コンテナ内の別 DB `mytimeline_perf` | 開発データを汚さない。`container_name` 固定のため、別プロジェクトとして並行起動はできない |
| バケット | `mytimeline-images-perf` | 画像アップロードの生成物を開発用と分ける |
| JVM | `-Xms512m -Xmx512m` | ヒープを固定して毎回同じ条件にする |
| コンテナ上限 | CPU 2 / メモリ 1 GB | 同上 |
| テストデータ | SQL で直接投入（`perf/seed/seed.sql`） | API 経由は BCrypt が律速で遅い。Flyway には含めない |
| 後片付け | `down` が DB とバケットを入れ物ごと削除 | テスト中に増えたデータも含めて残さない |

H2（結合テスト用）は計測対象にしない。実行計画もロックの挙動も PostgreSQL と異なり、数値に意味がない。

### 15.5 認証の扱い

リフレッシュトークンはローテーションし、使用済みトークンの再提示を盗用とみなして**そのユーザーの全セッションを失効**させる（[F01_auth.md](features/F01_auth.md)）。負荷テストが自分でセッションを壊さないよう、次の決まりにする。

- 仮想ユーザー（VU）1 つにシードユーザー 1 人を割り当てる
- 通常のシナリオでは refresh を使わず、アクセストークン（15 分）の期限が近づいたらログインし直す
- refresh / logout は専用ユーザーで、1 VU の中で直列にだけ実行する

### 15.6 テスト種別

すべて実装済み。VU 数と時間は環境変数で一時的に変えられる（[perf/README.md](../perf/README.md)）。

| 種別 | 負荷形状 | 目的 | 合否 |
|---|---|---|---|
| smoke | 2 VU・1 分 | 環境とスクリプトの健全性確認。他の種別の前に必ず流す | エラー 0 件 |
| load | 50 VU まで 2 分で上昇、10 分維持。並行して画像つき投稿を毎分 12 件 | 通常負荷でのベースライン | read / write の p95 < 1 秒、失敗率 < 1 %。画像つき投稿は p95 < 3 秒（暫定） |
| stress | 200 → 400 → 800 → 1600 VU を 3 分ずつ | 限界点とボトルネックの特定 | 付けない。失敗率 5 % 超で自動中断 |
| spike | 平常 10 VU → 10 秒で 300 VU、1 分維持 → 平常 10 VU を 2 分 | 急増時の挙動と回復 | 急増後の区間が p95 < 1 秒、失敗率 < 1 % |
| soak | 30 VU・60 分 | ヒープ増加・接続リーク・トークン再取得 | load と同じ |
| focus | 同じ到着率（20 req/s）で 40 秒ずつ、条件違いの対を順に流す | TBD-09 / 12 / 13 とログインの個別計測 | 付けない（記録のみ） |

**ワークロードモデル**（load / stress / spike / soak で共通。`perf/k6/lib/flows.js`）: 1 反復 = 1 つの行動 + 思考時間 1〜3 秒。比率は SNS の読み取り偏重を想定した初期値で、実トラフィックの計測値ではない。

| 行動 | 比率 |
|---|---|
| 全体タイムラインを 1〜3 ページ読む（cursor で辿る） | 50 % |
| フォロー中タイムライン | 20 % |
| タイムラインで見かけた投稿を開く（詳細 + コメント一覧） | 8 % |
| プロフィールとユーザー投稿 | 5 % |
| ユーザー検索（ヒットあり 8 割 / なし 2 割） | 5 % |
| いいね → 解除 | 5 % |
| コメント投稿 | 3 % |
| テキスト投稿 | 3 % |
| フォロー → 解除 | 1 % |

画像つき投稿は MinIO の影響が大きいので、この比率には入れず、load の中で一定の到着率の独立シナリオとして流す。既定の画像は 1×1 px の PNG で、測れるのは形式検証と S3 への保存の往復まで（転送量は含まない）。

### 15.7 テスト設計技法との対応

単体・結合テストと同じく、どの技法からケースを導いたかを k6 の `group` 名とシナリオ名に書く。

| 技法 | 性能テストでの使い方 |
|---|---|
| 同値分割 | 負荷を 読み取り / 書き込み / 認証 / アップロード の 4 クラスに分け、`type` タグで別々に集計する |
| 境界値 | `limit=20`（既定）と `50`（上限）、アクセストークンの 15 分境界（soak）、stress で見つけた限界点の前後、フォロー数の多寡（一般ユーザーと「ほぼ全員をフォロー」のヘビーユーザー） |
| 状態遷移 | ログイン → refresh → ログアウト、いいね → 解除、フォロー → 解除 |

### 15.9 結果の記録

`perf/results/` は git 管理外。比較に使う数値だけをここに転記し、履歴を git に残す。**数値は下記のマシンでの値で、別のマシンや本番の数値とは比較できない。**

#### 2026-09-21（初回ベースライン）

- コミット: `6ea2792`（main）。マシン: Apple M3、Docker Desktop に 8 CPU / 8 GB を割り当て。backend コンテナは CPU 2 / メモリ 1 GB / ヒープ 512 MB
- データ量: 既定（users 1,000 / posts 100,000 / follows 約 52,000 / likes 約 300,000 / comments 200,000）。各回の前に `seed` を流し直した
- 応答時間は p95、単位はミリ秒

| 種別 | 条件 | リクエスト数（毎秒） | read | write | 失敗率 | backend CPU（上限 200 %） | 判定 |
|---|---|---|---|---|---|---|---|
| load | 既定（50 VU） | 18,761（24） | 12.5 | 9.8 | 0 % | 平均 12 % / 最大 25 % | 合格 |
| stress | 50 → 100 → 200 → 400 VU、各 3 分 | 85,457（98） | 7.6 | 6.5 | 0 % | 平均 22 % / 最大 100 % | 限界に届かず |
| stress | 400 → 800 → 1600 VU、各 2 分 | 203,306（419） | 8.3 | 11.2 | 0 % | 定常 約 60 % / 段の切り替え時に最大 206 % | 限界に届かず |
| spike | 既定（10 → 300 VU） | 11,600（41） | 急増後 17.9（急増中 312.6） | 急増後 12.6（急増中 96.4） | 0 % | 最大 204 % | 合格 |
| soak | 短縮（2 VU・16 分） | 1,027 | 22.3 | 19.6 | 0 % | — | 合格 |

load でのエンドポイント別（p95、ミリ秒）: `GET /api/timeline/following` 14.4、`GET /api/timeline/all` 12.5、`GET /api/users/{username}/posts` 12.5、`GET /api/users/search` 10.8、`POST /api/posts` 12.0、画像つき投稿 34.5。それ以外は 10 未満。

focus（20 req/s、各 40 秒。ログインのみ 5 req/s）:

| 対 | 条件 | p95（ミリ秒） | 関連 |
|---|---|---|---|
| タイムラインの件数 | `limit=20` / `limit=50` | 13.8 / 15.4 | TBD-09 |
| フォロー数 | 約 50 人 / 約 1,000 人 | 12.0 / 17.0 | TBD-13 |
| ユーザー検索 | ヒットあり / なし | 9.4 / 7.2 | TBD-12 |
| ログイン | — | 83.2（中央値 79.5） | TBD-17 |

**所見**

1. **読み取り・書き込みは基準（p95 1 秒）に対して 2 桁の余裕がある。** 1600 VU（毎秒 約 420 リクエスト）でも p95 は 約 10 ミリ秒、失敗 0 件で、このマシンでは定常状態の限界に届かなかった。50〜400 VU の stress では DB 接続の取得待ちも累計 3.4 秒（約 10 万回の取得に対して）で、無視できる
2. **唯一の弱点はログインの集中。** ログイン 1 回は BCrypt で約 80 ミリ秒の CPU を使うため、CPU 2 個では毎秒 25 回前後が上限になる。spike（10 秒で 300 人）ではログインの p95 が 7.9 秒、stress の段の切り替え（30 秒で 800 人増）では 13.4 秒まで悪化し、その間は読み取りも巻き添えで遅くなった（spike 中の read p95 312.6 ミリ秒）。それでも失敗は 0 件で、急増が収まると元の性能に戻った
   - **巻き添えの原因は DB 接続の枯渇。** `AuthService.login` は `@Transactional` の中で BCrypt の照合を行うため、照合が終わるまで DB 接続を握り続ける。ログインが集中すると HikariCP の 10 本（既定値）がログインに占有され、無関係なリクエストが接続待ちになる。`hikaricp_connections_acquire_seconds` の累計待ち時間は、spike で約 2,140 秒、1600 VU の stress で約 8,300 秒（最大 10.5 秒の待ち）増えた。接続タイムアウト（`hikaricp_connections_timeout_total`）は 0 件
   - 対策の候補は、照合をトランザクションの外に出すこと（接続を握る時間が数ミリ秒になる）。アプリ側のレート制限（TBD-17）も同じ症状を和らげる。対応は [#67](https://github.com/koma236/MyTimeline/issues/67) で扱う
3. **TBD-09 / 12 / 13 は現在のデータ量では問題にならない。** 条件を変えた対の差はいずれも数ミリ秒。ユーザー検索は全件走査だが 1,000 人では 10 ミリ秒未満で、影響が出るのはユーザー数が桁違いに増えてから。検証するなら `PERF_USERS` を増やして focus を流し直す
4. アクセストークンの 15 分境界は問題なし。soak（16 分）で期限切れ前の取り直しが 2 回、401 を受けてからの取り直しは 0 回。load（13 分）でも取り直し 16 回で失敗なし

**未実施**: soak の既定（30 VU・60 分）。ヒープ増加と接続リークの確認はこれから。参考として、約 1 時間の連続計測を通じて backend コンテナのメモリは 554 MiB から 720 MiB に増えたが、ヒープ使用量は stress 直後で 95 MiB（上限 512 MB）だった。

**次に測るとき**: stress の既定の段はこの結果を受けて 200 → 400 → 800 → 1600 VU に引き上げた。上の 2 回の stress は段が異なるため、次回の既定での結果とは段ごとには比較できない。

### 15.10 今回の範囲外

# 16. E2E テスト（Playwright）

> **前提:** 対象は **ブラウザから見たアプリ全体**（React + Vite の本番ビルド → Spring Boot → PostgreSQL / MinIO）。実行場所はローカルの Docker Compose と CI。実行手順は [e2e/README.md](../e2e/README.md) を参照。

### 16.1 位置づけ

| 層 | 何を確かめるか | 道具 |
|---|---|---|
| 単体・結合 | 1 つの部品・1 つの API が仕様どおりか | Vitest / JUnit + H2 |
| API 負荷（[13_performance_test.md](13_performance_test.md)） | サーバーが負荷に耐えるか | k6 |
| **E2E（本書）** | **画面 → API → DB を通して、ユースケースどおりに機能が繋がって動くか。ブラウザ側の性能** | Playwright |

- シナリオ・耐性・アクセシビリティは **PR ごと・main への push ごとに CI で実行する**（`.github/workflows/e2e.yml`。約 5 分。main の必須ステータスチェック）。テストコード自体の Lint / 型チェックは `quality-check.yml` の `e2e-static` ジョブが行う。手元では任意のタイミングで実行し、quality-check スキルの必須項目にはしない（Docker と隔離 DB が要る）
- ブラウザ性能の計測は **手動のみ**。共有ランナーの数値は安定せず、合否を自動判定しても信用できない

### 16.2 ツール

[Playwright](https://playwright.dev/)（`@playwright/test` 1.63、chromium のみ）。

| 理由 | 内容 |
|---|---|
| フロントと同じ TypeScript | 型定義と lint の流儀を共有できる。テストコードも PR で差分を読める |
| 複数のブラウザコンテキストを 1 テストで持てる | 「A がフォローすると B の画面ではフォロワー数が増える」のような 2 ユーザーのシナリオを 1 本で書ける |
| `request` API | 前提データ（相手ユーザー・既存の投稿）を API で速く作れる。画面で作ると前提づくりの失敗と本題の失敗が区別できない |
| 性能計測が同じコードで書ける | `PerformanceObserver` / CDP（`Performance.getMetrics`）にそのまま届く |
| 失敗の調査がしやすい | トレース（操作・通信・DOM のスナップショット）を失敗時だけ残す |

検討して採らなかったもの:

| 候補 | 判断 |
|---|---|
| Cypress | 複数コンテキスト（2 ユーザー同時）が不得手、並列実行が有償、性能計測 API が弱い |
| WebdriverIO / Selenium | Selenium プロトコル経由で遅く設定量が多い。得られるものが Playwright と変わらない |
| Lighthouse | ページ単位の監査で「操作の反映時間」が測れない。読み込み指標は Playwright で直接読めるので、今回は入れない（16.10） |

### 16.3 テスト環境

| 項目 | 設定 | 理由 |
|---|---|---|
| フロントエンド | `vite preview`（本番ビルド、ポート 4173）。Playwright が自動起動 | dev サーバーは非バンドル・非 minify で性能の数値に意味が無い。機能テストも同じサーバーに揃えて二重管理しない |
| backend | 開発用と同じ compose に `e2e/docker-compose.e2e.yml` を重ね、DB `mytimeline_e2e` / バケット `mytimeline-images-e2e` を向かせる | 開発データを汚さない（perf と同じ方式）。CPU・メモリの上限は付けない（測るのはブラウザ側） |
| テストデータ | 各テストが API で一意なユーザーと前提データを作る。実行のたびに全テーブルを空にする | テスト同士が独立し並列に流せる。毎回同じ状態から始まる |
| ログイン | `/api/auth/login` を `context.request` で呼び、Set-Cookie（リフレッシュトークン）をブラウザに入れてから画面を開く | アクセストークンはメモリ、リフレッシュトークンは httpOnly Cookie なので `storageState` では再現できない |
| セレクタ | ロール・ラベル・文言（`getByRole` / `getByLabel`）。`data-testid` は使わない | 利用者と支援技術が見るのと同じ手がかりで操作する。フロントのソースを変えずに済む |

**refresh の扱い**は k6 と同じ（[13_performance_test.md](13_performance_test.md) 15.5）。テストの API クライアントは Bearer トークンだけを使い、refresh を呼ばない。ブラウザの Cookie と食い違うと全セッションが失効する。

### 16.5 シナリオでは足りない観点

| ファイル | 内容 | 理由 |
|---|---|---|
| `robustness/resilience` | `page.route` で応答を差し替える。タイムライン取得が 500 → エラーと「再読み込み」で復帰。API が 401 → 自動リフレッシュして再送、画面は壊れない。refresh も 401 → ログイン画面へ。接続不能 → 接続エラーの文言。投稿の送信失敗 → 入力内容が残り再送で通る | 単体テストはモックした axios で `client.ts` を見ているだけ。集約リフレッシュと再読み込みの導線を実ブラウザで確かめる |
| `a11y/accessibility` | axe-core（WCAG 2.1 A / AA + best-practice）で SCR-01〜07 を代表的な状態で検査。serious / critical の違反が **既知（16.8）以外に** 無いこと | 支援技術で使えるかは手で見ても分からない。初回で 3 件見つかった |
| 全テスト共通 | ブラウザの未捕捉例外と `console.error` を自動収集し、1 件でもあれば失敗 | 画面上は動いて見えても React が例外を握りつぶしている場合を拾う |

### 16.6 ブラウザ性能

`e2e/tests/perf/`。k6 が測るのはサーバーの応答時間だけで、「ボタンを押してから画面に出るまで」「最初の描画まで」はここで測る。

**計測方法**

- 時刻はすべて**ブラウザ内**で取る（`performance.now()` / `PerformanceObserver` / CDP）。Playwright と Node の往復は操作を起こす 1 回分（数十 ms）しか含まず、毎回同じだけ乗るので前回比較には影響しない
- 各操作を `E2E_PERF_RUNS`（既定 5）回繰り返し、**中央値で合否**を判定する。最小・最大は記録のみ
- 直列・1 worker・リトライ無しで実行する（`playwright.perf.config.ts`）
- 結果は `e2e/results/<日時>-perf.{json,md}`。比較に使う数値だけを 16.9 に転記する

**合否基準**

| 計測 | 内容 | 基準 | 出典 |
|---|---|---|---|
| 操作の反映時間 | 投稿 → 先頭に表示、いいね → ♥、タブ切替 → 一覧、無限スクロール → 次の 20 件、詳細へ遷移 → 投稿とコメント | 中央値 < 1,000 ms | [05_nonfunctional.md](05_nonfunctional.md)「通常操作は 1 秒以内に反映」 |
| ユーザー検索 | 入力 → 結果 | 中央値 < 1,300 ms | 上記 + SearchPage の debounce 300 ms |
| ページ読み込み | ログイン画面（未ログイン）とタイムライン（ログイン済み・投稿 60 件）を、キャッシュの無い新しいコンテキストで開く | TTFB < 800 ms、FCP < 1,800 ms、LCP < 2,500 ms、CLS < 0.1 | Web Vitals の "good" |
| 転送量 | 初期表示の JS（gzip） | < 250 KB | 暫定。増えたら分割を検討する目安 |
| 長いスクロール後の資源 | 200 件を読み切ったときの JS ヒープ・DOM ノード数、投稿 1 件あたりの増加 | ヒープ < 100 MB。他は記録のみ | 暫定。無限スクロールは読んだ分を DOM に積むので増え方を見る |

### 16.7 テスト設計技法との対応

| 技法 | E2E での使い方 |
|---|---|
| 同値分割 | ログインの識別子（username / email）、有効 / 無効な画像、該当あり / なしの検索、API 失敗の種類（500 / 401 / 接続不能） |
| 境界値 | 本文 280 / 281、コメント 500 / 501、自己紹介 300 / 301、パスワード 7 / 8、画像 4 / 5 枚、ページング 20 / 21 件 |
| デシジョンテーブル | 投稿の作者（自分 / フォロー先 / 無関係）× タブ、本人 / 他人 × 編集・削除メニュー、確認ダイアログの承諾 / 却下 |
| 状態遷移 | ゲスト → ログイン → ログアウト、投稿 → 編集 → 削除、いいね ⇄ 解除、フォロー ⇄ 解除 → フォロー中タイムライン、API 失敗 → 再読み込み → 復帰 |

### 16.8 アクセシビリティ検査で見つかった課題

初回（2026-09-22）の axe 検査で、7 画面に共通する serious の違反が 3 件見つかった（[#71](https://github.com/koma236/MyTimeline/issues/71)）。テストでは `KNOWN_VIOLATIONS` として記録のみにし、これ以外の serious / critical が増えたら失敗させる。直したら一覧から外す。

| ルール | 内容 |
|---|---|
| `color-contrast` | `text-muted` / `text-accent` の文字色が白背景に対してコントラスト比 4.5:1 に届かない |
| `link-in-text-block` | 本文中のリンク（「新規登録」「ログイン」）が色だけで区別されている |
| `link-name` | アバターを包むリンク（投稿・コメント・検索結果）が `aria-hidden` の画像しか持たず、読み上げ名が無い |

### 16.9 結果の記録

`e2e/results/` は git 管理外。比較に使う数値だけをここに転記する。**数値は下記のマシンでの値で、別のマシンや本番の数値とは比較できない。**

#### 2026-09-22（初回ベースライン）

- ブランチ: `feature/issue-70-e2e-playwright`（#70）。マシン: Apple M3 / 16 GB、macOS 26.5、Docker Desktop に 8 CPU / 8 GB。Chrome Headless Shell 153（Playwright 1.63）、Node 24
- backend は Docker（上限なし）、フロントは `vite preview`（gzip 配信）。すべて localhost なので TTFB は 1〜2 ms
- シナリオ: 58 件合格（scenario 46 / robustness 5 / a11y 7）。性能: 9 件合格。単位は ms、5 回の中央値（最小〜最大）

| 計測 | 中央値 | 最小〜最大 | 基準 |
|---|---|---|---|
| 投稿の反映 | 70 | 59〜104 | < 1,000 |
| いいねの反映 | 64 | 63〜96 | < 1,000 |
| タブ切替の反映（各 25 件） | 59 | 59〜83 | < 1,000 |
| 無限スクロールの次ページ | 66 | 57〜74 | < 1,000 |
| ユーザー検索の結果表示（debounce 300 ms 含む） | 342 | 333〜350 | < 1,300 |
| 投稿詳細への遷移（コメント 5 件） | 69 | 45〜79 | < 1,000 |
| ログイン画面 FCP / LCP / CLS | 48 / 60 / 0.000 | 44〜52 / 60〜80 | < 1,800 / < 2,500 / < 0.1 |
| タイムライン（60 件）FCP / LCP / CLS | 52 / 84 / 0.026 | 48〜56 / 80〜88 | < 1,800 / < 2,500 / < 0.1 |
| JS 転送量（gzip）/ CSS | 98.8 KB / 3.7 KB | — | < 250 KB |
| JS ヒープ 20 件 → 200 件表示後 | 3.7 MB → 11.3 MB | — | < 100 MB |
| DOM ノード数 200 件表示後 | 15,948（投稿 1 件あたり約 75） | — | 記録のみ |

所見:

- 操作の反映はどれも 100 ms 前後で、基準（1 秒）に対して十分な余裕がある。ローカルなので通信がほぼ 0 で、数値の大半は React の再描画と Playwright のクリック往復
- タイムラインの CLS 0.026 は、投稿が届く前に空の状態が描かれてから一覧に置き換わる分。基準内だが、件数が増えても値は変わらない（先頭 20 件分の高さ）
- 200 件で DOM が約 16,000 ノード・ヒープ 11 MB。仮想化（表示範囲だけ描く）は今のところ不要。1 件あたり 75 ノードは投稿カードの構造（メニュー・操作列・画像グリッド）そのもの

### 16.10 今回の範囲外

| 項目 | 理由 |
|---|---|
| Lighthouse のスコア | 読み込み指標は 16.6 で直接読んでいる。監査項目（SEO・PWA）はこのアプリでは重要でない。必要なら `lighthouse` パッケージを `tests/perf/` に足す |
| ビジュアルリグレッション（スクリーンショット比較） | 基準画像がマシンとフォントに依存し、CI と手元で一致しない。デザインが固まってから検討 |
| INP（操作の応答性の Web Vitals） | 実ユーザーの操作分布が要る指標。16.6 の「操作の反映時間」で代替している |
| モバイル・他ブラウザ | [05_nonfunctional.md](05_nonfunctional.md)「デスクトップを主対象、Google Chrome 最新版」 |
| 画像の転送量を含む性能 | 1×1 px の PNG で「形式検証 + 保存 + 署名付き URL」だけを見ている（k6 と同じ） |
